# Matter → Loxone Bridge — Roadmap

**Spec:** [`../specs/2026-09-01-matter-loxone-bridge-design.md`](../specs/2026-09-01-matter-loxone-bridge-design.md)

Each phase gets its own plan document and delivers runnable, testable software
on its own. A phase's plan is only written once the previous one is complete —
the order below is fixed, the details of later phases depend on the results
of the earlier ones.

## Order and rationale

| Phase | Delivers | Why here |
|---|---|---|
| **1. Matter adapter and signal extraction** | CLI that lists all attributes and events for a real device | Proves the core assumption from spec 3.5. If it breaks, the whole design breaks — that has to be settled first |
| ~~**2. dev profile**~~ | *deferred, see below* | — |
| **3. Exporter** | `VIU_*.xml` and `VO_*.xml` per device, golden-file tested against real Loxone Config | Format is verified (spec 6.1), risk is low. But needs the signal set from phase 1 |
| **4. Runtime path** | UDP sender, `commands/`, HTTP endpoint, `fake-miniserver` — end-to-end path to real Loxone | Only now do signals *and* Loxone objects both exist, with something able to flow between them. The `fake-miniserver` from phase 2 joins here, because only now does it have something to check |
| **5. WebUI** | Commissioning, signal management, operation, export, diagnostics, hardening | Needs everything below it. Diagnostics (spec 10.5) is what makes troubleshooting possible from here on. From this phase on the service can commission and remove devices — so it also brings the first access security |
| **6. Thread and deployment** | Production stack, deployment guide, system check | Isolable and non-blocking. Builds on the test environment from phase 1 |

## Deviation: phase 2 dropped (deferred 2026-09-02, dropped 2026-09-03)

Phase 2 was to deliver virtual Matter devices and a `fake-miniserver`. It was
first skipped and then dropped entirely on September 3, 2026 — **it will not
be picked back up.** Anyone passing through here does not need to schedule it
again.

The reason this became defensible: since September 3 the bridge has been
running against a real Miniserver, and that end-to-end run turned up four
bugs in a single day that no test had found — double-firing events, an
uninterpreted `onoff`, a format string over the Miniserver's limit, and an
inverted `Analog` attribute. Real hardware has thus become the feedback
channel that phase 2 was supposed to replace.

For the `fake-miniserver` this was the right order anyway: all three of its
capabilities presuppose code that only exists from phase 3 and 4 on — UDP
capture needs `loxone/out`, the command sender needs `loxone/in`, and
evaluating the generated `VIU_*.xml` needs both plus the exporter. It
therefore moves to phase 4.

For the virtual devices, it is a deliberately accepted bet. Phase 1 showed
that stand-ins had concealed two real bugs in `client.py` — the missing
listener and `node.attributes` instead of `node.node_data.attributes`. Both
would have surfaced through an integration test against a virtual Matter
device. **This bet stands, now permanently: CI only checks `client.py`
against stand-ins, and bugs of this class only surface on real hardware.**
That is the price of dropping the phase, not negligence — it needs to be
named so no one mistakes it for an oversight.

## Deviation: test environment pulled forward

Originally the entire container stack, including OTBR, was to be built only
in phase 6. That was wrong: phase 1 cannot fulfill its own task — checking
the assumption from spec 3.5 against real devices — without a running Matter
controller at all.

Phase 1 therefore now includes its own task that sets up matter-server and
OTBR on a Raspberry Pi (originally a Linux test VM — that was dismantled
because it lacked a Bluetooth adapter, and Matter commissioning runs over
BLE). Deliberately just a test environment, not a production stack: no
hardening, no deployment guide, no diagnostics page. Phase 6 builds on it and
inherits the record of what went wrong in practice.

## The risk that decides the order

Phase 1 comes first because it is the only phase that checks an **unproven
assumption**. All the others build on the known: the template format is
verified against a reference implementation, UDP behavior is confirmed
against a real Miniserver, the stack is established.

Whether a real IKEA device's cluster tree can be fully decomposed into
signals without special cases, on the other hand, nobody knows yet. The CHIP
example apps do not answer that — they are too well-behaved. If the answer
turns out negative, spec 3.5 changes, and with it the exporter, the data
model, and the WebUI. Having this insight in week one instead of week six is
the sole reason for this order.

## Rule for every phase

A phase counts as done when:

1. its tests pass without hardware and without network access,
2. its result has been confirmed by hand once against real hardware,
3. deviations from the spec are recorded there — the spec remains the
   authoritative document, not the plan.
