# Internationalization, phase B+C: API, WebUI, and export templates

Design, September 4, 2026. Continues [phase A](2026-09-03-i18n-phase-a-language-selection-cli-design.md)
(base language English, switchable to German; already built there:
`loxmatter.i18n.t()`/`strings.yaml`, the shared language setting in
`LocaleStore`, the fully translated CLI). Phase A had explicitly deferred
API+WebUI and the template texts — this design catches up on both,
together, by explicit request: phase C (template texts), at around nine
short fields, is small enough to attach to phase B (API+WebUI) rather than
justify its own design cycle.

Resolution of three open questions from phase A, settled before this
design: the template texts follow the shared language setting (not
hard-wired); the WebUI gets its translations through a new API endpoint as
JSON, not through a newly introduced templating engine (the WebUI has
none, see section 3); a language switch in the WebUI reloads the page,
instead of switching reactively without a reload.

## 1. Goal

The same one shared language setting from phase A now also controls: the
API's error messages (`HTTPException` `detail` texts), the entire WebUI
(static HTML text and the text generated by `app.js`), and the
title/comment fields in exported Loxone templates. The same mechanism
(`i18n.t()`, the same `strings.yaml`) is extended with three namespaces —
no second piece of infrastructure.

## 2. Non-goals

- No translation workflow beyond manual work — as in phase A, still
  reasonable at this increase in string count (around 120).
- No language per browser/user — unchanged, one setting for the whole
  installation (phase A, section 1).
- No templating engine (Jinja2 or similar) for `index.html` — see section
  3 for the reasoning.
- No retroactive translation of already-exported templates already
  imported into Loxone Config — only newly generated exports are
  affected, exactly as with a change to the signal selection (main
  document, README).

## 3. Namespaces in `strings.yaml`

Three new dotted prefixes alongside the existing `cli.*`:

| Prefix | Scope | Origin |
|---|---|---|
| `api.*` | `HTTPException(detail=...)` in `api/control.py`, `api/devices.py`, `api/auth.py`, `api/diagnostics.py`, `api/export.py` — around 29 call sites, plus `api.export.readme_text` for the text of `Import-Anleitung.txt` in the export ZIP | Python, server-side |
| `web.*` | Static text in `web/index.html` (~40) and text generated by `web/app.js` (~40) | JavaScript/Alpine, client-side |
| `export.*` | Title/comment fields in `export/documents.py` and `export/signals.py` (around nine strings) | Python, both server- AND CLI-side (both call the same functions, see main document section 4.2 and phase A's experience with `_load_snapshot`) |

`index.html` is currently delivered as a plain, unmodified file
(`FileResponse`, no Jinja2, no server-side rendering) — a templating
engine for the HTML file would therefore mean a new dependency AND solve
only half the problem, because the text generated by `app.js` at runtime
(toasts, computed labels) would remain unaffected by it and would need
its own client-side mechanism regardless. So delivery stays unchanged and
static, and `web.*` reaches the client instead through a JSON endpoint
(section 5).

## 4. Language resolution in the long-lived server process

Unlike the CLI (every call a new process, language resolved once at
module import, see phase A sections 4-5), `loxmatter run` runs as a
single, long-lived process. A one-time resolution at start (`build_app()`)
would leave a gap: if someone changes the stored setting via the CLI
(`loxmatter set-language`) while `loxmatter run` is already running, the
running server process would not see it — `LocaleStore` and
`BridgeSettingsStore` live in the **same** database, but `i18n.t()`'s
current language is state of **this one process**.

**A new middleware therefore reads the stored setting fresh on EVERY
incoming request** — before routing, before the login check, the same way
for every request (`/`, `/static/*`, `/cmd`, `/resync`, `/api/*`):

```python
@app.middleware("http")
async def sync_language(request: Request, call_next):
    i18n.set_language(store.locale.get_language())
    return await call_next(request)
```

This is not a new idea but follows an already-established pattern of this
project: `BridgeSettingsStore.get()` likewise reads freshly from the same
table on every call, with no cache of its own (see `settings_store.py`) —
a cache with its own invalidation would be an extra, unnecessary source of
bugs here. The cost is one extra, very small SQLite query per request;
`LocaleStore.get_language()` never raises (phase A, section 4), so a
database error at this point blocks no request.

**Consequence for `PATCH /api/language` (section 5):** the route itself
does NOT need to call `i18n.set_language(...)` — it only writes to the
database, and the next request (including this route's own response)
already reads the new setting via the middleware. This simplifies the
route compared with the path initially sketched in discussion (an
explicit `i18n.set_language()` call directly in the route, analogous to
phase A's fix to `set-language` in the CLI) — there an explicit call was
needed because the CLI has no middleware and every call is a new process
anyway; here the middleware takes on that role for EVERY request, not
just the one that changes the setting.

## 5. New routes

New, small module `api/language.py`, scoped analogously to
`api/settings.py`:

- **`GET /api/i18n`** — returns `{"language": "en", "strings": {"web.xyz": "...", ...}}`
  (only the `web.*` subset of `strings.yaml`, resolved in the currently
  set language). **Deliberately exempt from the login check** — the
  third, explicitly named exception alongside `/cmd` and `/resync`
  (WebUI login design, the section there on the first two exceptions),
  but for a different reason: not because a client cannot send a header,
  but because the initial-setup and login page itself needs this text in
  order to display at all — before any login. No security risk: the
  response contains no secrets, only translation text and the currently
  set language.
- **`PATCH /api/language`** — body `{"language": "de"}`, requires a valid
  session or a valid token like any other `/api` route (analogous to
  `PATCH /api/settings`). Calls `store.locale.set_language(...)`; raises
  `ValueError` (→ 400) for an unsupported value, exactly as
  `LocaleStore.set_language` already does from phase A.

`build_api_guard` (`loxone/server.py`) gets a third exception alongside
`/cmd`/`/resync`: `GET /api/i18n`.

## 6. API error messages (`api.*`)

Every `HTTPException(..., detail="...")` string in `control.py`,
`devices.py`, `auth.py`, `diagnostics.py`, `export.py` moves behind
`i18n.t("api.<module>.<purpose>", **values)` — mechanically identical to
phase A's CLI migration (sections 4-5 there), just a different call site.
This text is NOT a second translation for the WebUI: `app.js`'s
`readErrorDetail` (phase A investigation) already shows `detail` today
unchanged as the message — so the WebUI does not translate this text a
second time client-side, it simply shows what the API returns in the
currently active language (the middleware, section 4, ensures that is the
same language as the rest of the request).

## 7. WebUI (`web.*`)

**Load sequence.** `app.js`'s `init()` calls `GET /api/i18n` as the VERY
FIRST thing (before everything else that happens there today), fills an
Alpine store (`language`, `strings`), and only then does the UI become
visible — hidden until then via `x-cloak` (a CSS rule `[x-cloak] {
display: none }`, Alpine removes the attribute itself once initialized),
so no brief flash of raw `{key}` text or English text is visible before
the actually configured language.

**Translation helper.** A function `t(key, values = {})` in the Alpine
store, which reads the value from the loaded `strings` object and
replaces `{placeholder}` with `values` (the same `.format()` convention
as on the Python side, rebuilt here by hand as simple string substitution
— no new dependency for this little effort). Every static text in
`index.html` becomes `x-text="t('web.xyz')"`, or for attributes
(`placeholder`, `title`) `:placeholder="t('web.xyz')"`. Every string
generated in `app.js` (toasts, computed labels) calls the same `t()`.

**Language switcher.** The already-empty placeholder card "More settings"
in the Settings tab (`index.html`) becomes the EN/DE switcher — two
buttons instead of a dropdown (a binary choice). A click calls `PATCH
/api/language` and then reloads the page (`window.location.reload()`) —
the confirmed, simpler of the two variants considered (see design
discussion): no special case for toasts already shown or WebSocket state
that would otherwise be left in the old language.

## 8. Export templates (`export.*`) — phase C

The around nine title/comment fields in `export/documents.py` and
`export/signals.py` (e.g. `"erzeugt von loxmatter"`, `"Bridge
erreichbar"`, `"Alle Werte neu senden"`, `f"{signal.title} Zähler"`) move
behind `i18n.t("export.<purpose>", **values)`. Since the CLI and WebUI
call the same `export/*.py` code (phase A investigation, confirmed: no
duplication), the same currently-set-at-export-time language applies to
both — for the CLI, the one resolved at process start (phase A); for the
WebUI, the one read by the middleware (section 4) for the respective
request.

**Confirmed (design discussion):** the template texts follow the shared
setting, not a fixed language. Whoever switches the UI language and then
exports a device again gets titles in the other language — only for NEWLY
generated templates; a template already imported into Loxone Config stays
untouched (the same property as with a change to the signal selection,
see the README section on the update notice).

The text of `Import-Anleitung.txt` in the WebUI's export ZIP
(`api/export.py`, a prose block, does NOT exist in the CLI path — the CLI
does not bundle this file) is maintained as one key
`api.export.readme_text` with `en`/`de` versions. Whether and which values
are inserted into it (placeholders) is settled by the implementation plan
based on the actual, current text — not anticipated here.

## 9. Tests

Extends phase A's test strategy with the two new surfaces:

- **API:** as with the CLI (phase A, section 6) — existing tests that
  check literal German `detail` text switch to the new English default
  text; German counterparts are added via `i18n.set_language("de")`
  before the respective request.
- **Middleware:** a dedicated test proving that a value changed via
  `store.locale.set_language(...)` (directly through the database,
  without the API) is seen by the NEXT request to the same running test
  server/the same in-process ASGI instance — that is exactly the gap
  section 4 closes, and deserves a test that checks it specifically, not
  just one that happens to be covered implicitly by other tests.
- **`GET /api/i18n` without login:** a test that explicitly calls without
  a session and without a token and expects a 200 instead of a 401 — the
  new, deliberate third exception to the rule that otherwise applies
  (section 5).
- **WebUI:** no browser test framework in this project so far (see
  `tests/api/test_web.py`, which checks the returned HTML/JS text, not
  rendering it) — the implementation plan decides whether a check at the
  text level is sufficient (no raw `{key}` text in the delivered
  `index.html`/`app.js`, no more hard-coded German text in `app.js`) or
  whether Playwright or similar is newly introduced — a new dependency
  for that is rather NOT in the spirit of this project, but that is
  decided in the plan, not here.
- **Export:** existing snapshot/content tests of the generated XML files
  (`tests/export/`) switch to English default text, German counterparts
  added — as with phase A's `_load_fixture` tests.

## 10. Outlook

After this phase, every user-facing text in the project is bilingual —
CLI (phase A), API and WebUI (phase B), export templates (phase C). What
deliberately stays open: the middleware from section 4 makes `i18n.t()`
consistent at runtime within ONE server process; several `loxmatter run`
processes running simultaneously (not envisioned today anyway, see main
document non-goals: "Multiple Miniservers on one bridge") are not
accounted for — the same limit that already applies to `Store`'s
connection anyway (`model/store.py` module docstring: one store instance
belongs to exactly one thread).
